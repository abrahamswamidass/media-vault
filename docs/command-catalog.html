Media Vault · Agent CLI

Command Impact Reference

What every mediavault.cli command actually touches — the local SQLite catalog, the NAS/Drive connector, the cloud mirror (Cloud Storage + Firestore), or nothing at all. Cross-reference for setup.md, agent.md, and web.md, not a replacement for them.

Dry-run is the default Only the agent touches files One writer per collection
The three rules this table is really about (see CLAUDE.md): the web module never touches a NAS/Drive byte directly — it only writes an intent document, which process-intents claims and turns into one of the same Action classes every CLI command below uses. Every mutating command previews by default; nothing changes on disk or in the cloud until --commit is added.

Typical order of operations

1 · index

Walk the connector, populate the SQLite catalog. Nothing leaves the machine.

→

2 · dedup

Full-hash confirm candidates, archive exact duplicates to trash. Reversible.

→

3 · publish

Thumbnail + EXIF + (optional) faces → Cloud Storage & Firestore items/.

→

4 · web module

Reads items/; a click writes an intent — never touches a file.

→

5 · process-intents

Claims the intent, runs the matching Action, writes status/result back.

* dedup's full-content confirmation caches each hash into the catalog immediately, even in preview mode — that's a deliberate exception to "nothing changes without --commit": it's a pure cache of a fact already true on disk, not a mutation, and it's what makes a second dedup run skip re-reading files it already confirmed.
† deletes catalog rows for one source only, not files on the NAS/Drive — see the warning below.
‡ only with --purge-facts.
§ the actual columns written depend on which intent type was claimed — stage_for_amazon only touches NAS files, publish touches catalog/blobs/items, delete only touches the source connector, and so on. This row shows the union across every intent type in the registry.

Don't confuse reset with "clear the publish flag." It deletes every catalog row (quick_hash, EXIF, dedup state) for a source — recovering from an accidental run means a full re-index and re-hash of everything, not a quick fix. It never touches the NAS/Drive or already-published Cloud Storage blobs (those are content-addressed and safe to leave), but it is not a light undo button.

Firestore collection ownership

items/

Agent-only writes, via publish. Web module reads only.

intents/

Web-created (one write, never updated by the client). Agent owns status/claimed_at/result from there on.

agent_status/, hidden_folders/

agent_status/: agent-only, a process-intents --watch heartbeat. hidden_folders/: the one collection the web module owns outright — a display preference, not a file mutation, so it skips the intent round-trip entirely.
