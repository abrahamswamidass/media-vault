Media Vault · system design

Two one-way flows

A local agent at home holds the only keys to your files. A web module in Google Cloud is where you decide things. They never call each other — they meet in three document shapes, and each one has exactly one writer.

RULE 01
Only the agent touches files
The web module cannot read a byte off the NAS. It writes wishes; the agent decides whether to honour them.
RULE 02
Dry-run is the default
Every mutating path takes commit=False. A caller who forgets the flag gets a preview, never a mutation.
RULE 03
One writer per collection
There is no merge logic anywhere in this project, because no document ever has two authors.
The mechanism

Facts go up. Wishes come down.

Bidirectional sync is where projects like this die — conflict resolution, split-brain, arguments about which side won. Splitting the traffic into two independent one-way flows removes that entire category of problem. The NAS is the source of truth; if the cloud mirror ever disagrees, the next scan corrects it.

Where things live

Three collections, three owners

CollectionWritten byRead byHolds
items/ agent web A fact. This file exists on the NAS, is this big, hashes to this, and its thumbnail is at this key.
intents/ web agent A wish. Please delete this / fetch this / move this. The agent writes back status and result.
actions/ agent web A record. This happened, with these inputs, at this time. Append-only mirror of the agent's local journal.

intents/ is the one document with two hands on it, so the split is by field: the web module owns type, item_id and params and never touches the outcome; the agent owns status and result and never rewrites the request. Both sides validate against the same JSON Schema in shared/contracts/, so a shape change breaks both modules in the same commit rather than silently.

Thumbnails

Name blobs by content, never by path

This is the single most load-bearing decision in the sync design. Every derived image is keyed by the hash of the file it came from — not by where that file currently sits.

thumbs/15423a9f3c1.webp ← 400px WebP, ~30 KB, permanent
previews/preview/15423a9f3c1.jpg ← 2048px JPEG, ~500 KB, expires in 1 day
previews/original/15423a9f3c1.jpg ← untouched bytes, expires in 1 day

Uploads become idempotent

A re-scan derives the same key, so a HEAD check short-circuits the upload. This is exactly what closes the consumer-idempotency gap: a replayed intent finds the blob already there and reports no-op without touching the NAS.

Duplicates collapse for free

Two copies of the same photo — one on the NAS, one in a Takeout export — hash identically and share one blob. No dedup pass required to get the storage saving.

Renames cost nothing

Moving a file on the NAS invalidates no blob and triggers no re-upload. Only the pointer in items/ changes.

The hash itself never reads a whole file: it is the size plus a SHA-1 of the first and last 64 KB. Reading a terabyte over a network mount just to fingerprint it is not an acceptable cost, and for distinguishing photos this is plenty.

Full resolution

Looking at a photo is an intent too

Thumbnails are enough to decide keep or bin, but not to actually look at something. The full-resolution bytes stay at home — so viewing one becomes a request like any other, and you pay egress only on what you actually opened.

Two variants. preview is a 2048px JPEG at around 500 KB — the default, and what you want for judging a photo. original is the untouched bytes, for when you actually want the file; a 50 MB RAW costs about half a cent in egress, which is fine occasionally and wrong as a default.

One rule is load-bearing: a lifecycle rule on the bucket must delete previews/ after a day. Thumbnails are permanent; previews are disposable by design, and without that rule they accumulate silently and turn a fixed 6 GB mirror into a growing one.
Deduplication

Within a source, never across it

The NAS holds everything. Drive holds a curated copy of the good things. Amazon receives the occasional push so something shows up on a TV. So a photo existing in both the NAS and Drive is the system working — and the grouping query is scoped to one source precisely so that pair is unreachable by any code path here.

Exact → archived automatically

Identical bytes, confirmed by a full SHA-256 across the group. One copy always survives; the rest move to trash and stay recoverable.

Near → flagged for review

A re-compression or a resize is similar, not identical, and one of the pair is usually the better file. That call is yours, so it never happens automatically.

The survivor is the oldest

Tie-broken by shallowest path, then alphabetically. Deterministic, so a second run proposes exactly the same thing — and the dry-run names the keeper for every group.

A fingerprint match is not proof. quick_hash is the file size plus a hash of the first and last 64 KB, so two files can share one and still differ in the middle — unlikely for photos, entirely plausible for video. Anything above 128 KB is fully hashed before it is archived. Below that, the two windows already overlap and cover every byte, so no second read is needed.

Stack

Firebase, and no backend service at all

For a single-user system, Firebase Auth + Firestore + Storage + Hosting with security rules locked to one account means there is no server in the middle. React talks to Firestore directly. Nothing idles, nothing needs patching, and there is no container to keep warm.

Why not Cloud Run

A relay service would exist only to forward reads the client SDK can already make safely. Security rules do that job with no compute and no cost.

Listen, don't poll

Polling Firestore every 5s burns ~17k reads/day out of a 50k free tier while doing nothing. A snapshot listener bills only on real changes — with a slow 5-minute poll behind it in case the connection drops.

Deploys from GitHub Actions

Firebase Hosting has a first-party action, so the web module ships on push with a service-account secret and no custom pipeline.
